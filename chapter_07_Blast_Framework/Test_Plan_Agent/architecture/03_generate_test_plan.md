# SOP 03 — Generate the Test Plan

**Layer:** 1 (Architecture)
**Tools:** `tools/plan_generator.py`, `tools/template_loader.py`
**LLM:** Groq (`openai/gpt-oss-120b` by default)
**Status:** Active

---

## Goal

Turn one `JiraIssue` into a complete, enterprise-grade, **traceable** Test Plan
(Markdown) — deterministically, without inventing facts. The document shape is
driven by the user's own template, not by code.

## Inputs

- `JiraIssue` (SOP 02)
- `templates/testplan_template.md` — **authoritative structure**
- `templates/VWO_Test_Plan.md` — **authoritative test-case format**
- settings: `groq_api_key`, `groq_model`, `plan_depth` (`standard` | `detailed`)

## Structure (from the template — never hardcoded)

`template_loader` derives everything from the files at runtime:

| Function | Produces |
|---|---|
| `required_sections()` | Numbered top-level sections → used by `validate_plan` |
| `structure_digest()` | Each heading + the **exact table it expects** + `<placeholder>` guidance |
| `master_digest()` | The test-case table header + ID scheme (deduped) |
| `outline_text()` / `all_sections()` | Compact outline / every numbered heading |

Current top-level sections: **1. Introduction · 2. Test Level · 3. Test Reporting
and Defect Tracking · 4. Change Management · 5. Test Planning · 6. Customer
Validation Plan** (plus 25 sub-sections and 12 tables).

If no template file exists, `DEFAULT_SECTION_TITLES` is used as a fallback.

## Prompt budget — HARD CONSTRAINT ⚠️

Groq meters `openai/gpt-oss-120b` at **8,000 tokens/minute** on the free tier,
and **only the prompt is metered** (`max_tokens` does not count — verified).

- **Never embed the template/master verbatim** (that produced a 12,302-token
  prompt → HTTP 413).
- Use the derived digests instead. Current prompt ≈ **3,300 tokens**.
- The offline test suite asserts the prompt stays < ~7,000 tokens.

## Test-case contract (from the master)

- Columns exactly: `| Test case id | Description | Actual Result | Expected result | Requirement ID | Dependencies |`
- **"Actual Result" is left blank** — filled at execution time.
- IDs `<PROJECT>-<AREA>-<NNN>_<T>`, T ∈ {P, N, B, E}; grouped into suites S1..Sn.
- A requirement coverage matrix `| Requirement | Suites covering it | Status |`.

## Generation rules (embedded as code constants)

- Use **only** facts from the `JiraIssue`. Missing → `Not specified` /
  `<to be confirmed from actual build>`.
- Never invent features, people, environments, dates, owners, or numeric SLAs.
- Any inference is visibly labelled `(inferred)` / `(proposed)` / `(assumption)`.
- Each table goes **only** under the heading whose `table:` line specifies it.
- Tone: precise, enterprise QA documentation. Document only — no preamble.
- Depth minimums: `standard` = 4+ suites / 12+ cases; `detailed` = 8+ suites /
  25+ cases, plus risks and metrics minimums.

## LLM call

`POST https://api.groq.com/openai/v1/chat/completions`
`Authorization: Bearer {groq_api_key}`, `temperature=0.2`, `max_tokens=16000`.
Failures raise a typed, user-presentable `GroqError` — including a specific
message for **HTTP 413** (request exceeds the tier's TPM limit).

## Meta

Emitted deterministically as an HTML provenance comment
(`<!-- Generated by Test Plan Creator | Jira <key> | <ts> | <model> | depth <d> -->`);
the template supplies its own title page.

## Post-generation validation

`validate_plan(markdown)` checks the template's numbered top-level sections and
returns any missing ones. The caller shows a non-fatal warning (the document is
still displayed). Un-numbered headings (Copyright Notice, Appendix) are excluded.

## Determinism

`temperature=0.2` + sorted list inputs + a fixed, file-derived outline.
Re-running on the same ticket must produce a structurally identical plan.

## Golden rule

If this logic changes, **update this SOP before changing the code.**
